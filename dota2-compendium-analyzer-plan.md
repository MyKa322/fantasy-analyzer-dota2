# Dota 2 Compendium Analyzer — техническое задание и план разработки

Цель приложения: точечный, приближённый к реальности анализ команд и игроков TI15 для раздела Predictions и Fantasy Draft компендиума. Ниже — весь стек, источники данных, и отдельно разобранная методология для команд и для игроков, с опорой на то, как это уже делает комьюнити (datdota, Liquipedia, GitHub-проекты энтузиастов, форумы).

---

## 0. Контекст: что именно мы прогнозируем

Компендиум TI15 (13–23 августа, Шанхай) по датамайну повторяет структуру прошлого года: два независимых блока начисления очков — **Predictions** и **Fantasy Draft** — каждый на два периода (Road to The International и сам турнир), с отдельным ростер-локом на каждый период. Награды идут по перцентилю участников (топ-15% что-то получают, топ-0.1% — максимум).

- **Predictions** — командный уровень: угадать итоговый счёт группы (4-0, 4-1 и т.д.) и результаты сетки плей-офф. Это чистая задача "кто сильнее и с какой вероятностью".
- **Fantasy Draft** — игроковый уровень: собрать состав из 3 профессиональных игроков (керри/мид/саппорт), каждый игрок приносит очки за реальные игровые действия в матчах TI. Это задача "сколько очков наберёт конкретный игрок", а не "кто победит" — итог матча на Fantasy-очки не влияет.

Это две разные аналитические задачи с разными входными данными, поэтому ниже они разобраны отдельно (разделы 3 и 4).

## 1. Стек разработки

| Слой | Технология | Почему |
|---|---|---|
| Бэкенд | Python + FastAPI | Прямой доступ к pandas/numpy/scikit-learn для аналитики, асинхронные запросы к нескольким внешним API одновременно, автогенерируемая документация (`/docs`) |
| БД | SQLite (личное использование) → PostgreSQL (если решишь выложить как сайт) | Для одного пользователя SQLite не требует отдельного сервера; миграция на Postgres — это просто смена `DATABASE_URL` благодаря SQLAlchemy |
| Фоновые задачи | APScheduler (в процессе приложения) | Раз в несколько часов подтягивать новые матчи и пересчитывать рейтинги; Celery+Redis имеет смысл только при реальной многопользовательской нагрузке |
| Фронтенд | React + TypeScript + Vite + Tailwind | Быстрая разработка, типобезопасность важна при работе с API-ответами, которые меняются по ходу турнира |
| Графики | Recharts | Тренд рейтинга команды во времени, распределение вероятностей по итоговому счёту группы |
| ПК-приложение | Tauri-обёртка над тем же веб-фронтендом | Не нужно писать интерфейс дважды: тот же React-код даёт и сайт, и нативный .exe/.app (легче Electron) |

## 3. Анализ команд (модуль Predictions)

### 3.1 Почему именно Glicko-2

Это не только моя рекомендация — это то, на чём уже стоит индустрия. Два факта, которые стоит знать перед тем, как спорить с этим выбором:

- **datdota.com** годами публикует рейтинги команд по Elo (отдельно с k=32 и k=64) и по Glicko-2 одновременно — это открытые, постоянно обновляемые рейтинги, на которые ориентируется часть комьюнити.
- **Liquipedia** — основная вики комьюнити — в июне 2026 полностью перезапустила свою систему рейтинга команд именно на Glicko-2, отказавшись от прошлой сложной модели, основанной на индивидуальных перформансах игроков. Причина, которую они сами называют: старая модель была точнее в теории, но не резонировала с комьюнити на практике. Для листинга команды требуют RD (неопределённость) ниже 100 и хотя бы один матч за последние 8 недель — разумный практический фильтр, который стоит скопировать.

Это прямое подтверждение того, что связка "рейтинг + явно выраженная неопределённость" — рабочий и проверенный подход для именно этой игры, а не абстрактная теория.

### 3.2 Как это работает (конспект — реализация уже есть и протестирована)

Каждая команда хранится как тройка `(рейтинг, RD, волатильность)`. После каждого нового матча Glicko-2 обновляет все три числа: неожиданный результат сильнее двигает рейтинг команды с малой историей (высокий RD), чем команды с полусотней стабильных игр за спиной. Разница рейтингов двух команд конвертируется в вероятность победы через логистическую функцию.

В этом чате уже реализован и провалидирован модуль на эталонном примере из оригинальной статьи Гликмана (совпадение до второго знака) — к нему вернёмся, когда перейдём к скелету.

### 3.3 От рейтинга к прогнозу очков

Сам рейтинг — это ответ на вопрос "кто сильнее". Compendium просит счёт (4-0, 4-1…) и результат сетки — для этого поверх рейтинга нужна **Monte-Carlo симуляция**:

1. Для каждой пары команд в группе рейтинг даёт вероятность победы.
2. Группа "разыгрывается" виртуально несколько тысяч раз со случайным исходом каждой игры, взвешенным этой вероятностью.
3. По итогам симуляций считается распределение: с какой вероятностью команда закончит 4-0, с какой — 3-1-1 и т.д.

То же самое рекурсивно для сетки плей-офф: вероятность дойти до полуфинала = вероятность выиграть все матчи до него.

### 3.4 Что взвешивать поверх базового рейтинга

- Затухание старых матчей (свежая форма важнее матча полугодовой давности)
- Стабильность состава — через Liquipedia; свежая замена игрока обнуляет часть доверия к истории команды
- Результаты именно на текущем патче отдельно от прошлого
- LAN против онлайн (часть команд играет заметно иначе)
- Личные встречи между конкретными командами, если данных достаточно

## 4. Анализ игроков (модуль Fantasy Draft)

Это отдельная, более специфичная задача, и вот почему её нельзя решать той же моделью, что и Predictions.

### 4.1 Как устроена механика (по актуальному гайду на прошлый TI, структура в датамайне TI15 заявлена той же)

Собираешь состав из 3 игроков-участников TI (керри/мид/саппорт). У каждого игрока — "боевой штандарт" (war banner) из 3 эмблем:

- **Цвет эмблемы** определяет категорию статистики: красная — соло-перформанс, зелёная — командная игра, синяя — саппорт-действия. У керри — 2 красных + 1 зелёная, у саппортов — 2 синих + 1 зелёная, у мидов — все три цвета доступны.
- **Стата эмблемы** — конкретный трекаемый показатель (GPM, число килов, собранные руны и т.п.) — это и есть основа очков, все проценты множатся именно на неё.
- **Тир эмблемы** даёт множитель от +10% (1 тир) до +150% (5 тир).
- Дополнительно у каждого игрока есть титулы (ещё одни условные множители — например, бонус за игру героем с рогами/крыльями).

**Критично для моделирования:** очки за период — это сумма по **двум лучшим картам лучшей серии** игрока. Если игрок сыграл десять Bo3, засчитается только одна серия — та, где он выступил сильнее всего, и внутри неё отбрасывается худшая карта. Это значит, что нужно моделировать не средний перформанс игрока, а **распределение его потолка** (по сути — статистику максимума из N попыток), иначе модель будет систематически недооценивать "нестабильных но взрывных" игроков, которые как раз выигрывают Fantasy.

### 4.2 Таблица начисления очков (актуальный формат прошлого TI)

| Действие | Очки |
|---|---|
| Убийство | +121 |
| Смерть | база 1800, −180 за каждую |
| Крип (добивание/деним) | +3 за каждый |
| Gold per minute | GPM × 2 |
| Захват Наблюдателя (Observer takeover) | +121 |
| Вард (Observer) | +113 |
| Стак лагеря | +170 |
| Руна (подобранная/забутыленная) | +121 |
| Разрушенная башня | +340 |
| Килл Рошана | +850 |
| Килл Торментора | +850 |
| Килл курьера | +850 |
| Первая кровь | +1700 |
| Дым обмана (использование) | +283 |
| Участие в тимфайте | до 1895 за карту (точная формула не раскрыта) |
| Стан (наложенный) | +128 за секунду |

Точные веса Valve может скорректировать под TI15 — держи эти цифры в конфиге, а не захардкоженными, чтобы обновить в один клик, когда выйдет официальный гайд.

### 4.3 Как это ложится на данные OpenDota

Почти все категории выше напрямую есть в разобранном матче OpenDota (`/matches/{id}`): `kills`, `deaths`, `last_hits`, `denies`, `gold_per_min`, `obs_placed`, `camps_stacked`, `rune_pickups`, `tower_damage`/лог событий разрушения башен, `stuns` (суммарная длительность), количество килов Рошана по таймлайну, покупки предметов (для Дыма обмана — через `purchase_log`). Участие в тимфайтах и первая кровь тоже вычисляются из объектных данных матча. То есть отдельного API не нужно — нужен ingest-модуль, который раскладывает то же самое тело матча, что уже используется для рейтинга команд, по этим полям на уровне игрока.

### 4.4 Метод прогноза

1. Для каждого кандидата в ростер — вытащить историю его матчей (OpenDota `/players/{account_id}/matches` + разбор `/matches/{id}` для нужных полей) за текущий патч и последние ~2-3 месяца.
2. По каждой категории очков — не просто среднее, а распределение (важно из-за правила "считаются только лучшие карты", см. 4.1). Оценка через эмпирические перцентили или через параметрическую модель (например, GPM неплохо ложится на нормальное распределение, килы/смерти — на что-то ближе к Пуассону).
3. Смоделировать N виртуальных серий: для каждой — выбрать 2 максимальные "карты" из распределения, просуммировать по формуле из 4.2, учитывая тир/титул конкретной выпавшей эмблемы.
4. Результат — не одно число, а распределение ожидаемых Fantasy-очков с доверительным интервалом, что прямо отвечает на вопрос "точечный анализ" из исходного запроса.
5. Дополнительно взвесить: пул героев игрока на текущем патче (эмблемы могут требовать конкретных условий), склонность его роли/команды забирать конкретные объекты (например, саппорт vs керри для Рошана — у команды это обычно не рандом, а паттерн).

### 4.5 Подтверждение подхода из комьюнити

Ты просил свериться с тем, что уже обсуждают — вот что нашлось по факту:

- **`RRDito/Dota-Fantasy-Database`** (GitHub) — открытый проект, который делает ровно это: парсит Liquipedia за match ID нужного турнира, тянет данные по этим матчам из OpenDota и считает Fantasy-очки, с сравнением перформанса двух игроков и графиком очков по длительности игры. Прямое подтверждение, что связка OpenDota + Liquipedia — это рабочий, уже проверенный кем-то ещё пайплайн именно для этой задачи.
- **`bydoodle/dota2fantasy`** — калькулятор Fantasy-лиги под TI2025, данные берёт через STRATZ (нужен токен с stratz.com). Второй пример того же паттерна с другим источником матчевых данных.
- Классический **Fantasy Dota** (ещё догеймовый режим, отдельный от Compendium) использует похожий принцип "засчитывается только лучшая игра серии" — это не разовая причуда TI2025, а устоявшийся паттерн механики Valve, так что стоит рассчитывать, что он останется и дальше.

## 5. Общая методология прогнозирования матчей — что уже пробовало комьюнити

Насколько сложна задача "предсказать исход матча" в принципе — по открытым проектам и статьям:

- Стэнфордский проект по рекомендации героев на выборке 50 000+ матчей получил **~63% точности** предсказания исхода на одних только пиках героев логистической регрессией — это ориентир "пола" точности для чисто предматчевых моделей без учёта силы команд.
- Публичные репозитории (`michaelge233/dota2_predictor`, серия постов на dev.to про Dota 2 Match Outcome Predictor) используют одинаковый паттерн: Python + pandas/scikit-learn, фичи на основе истории игроков/команд, логистическая регрессия или градиентный бустинг как модель.
- Аналогичный, более зрелый пример на соседней игре — `cs2-match-prediction` на GitHub — прямо документирует важный практический урок: **хронологическое построение фичей**, чтобы модель не подглядывала в будущее ("data leakage"), плюс сравнение нескольких алгоритмов (Logistic Regression, Random Forest, XGBoost, LightGBM) с калибровкой вероятностей, а не только бинарной точностью. Этот же принцип стоит перенести в свой ingest: рейтинг команды на момент матча должен считаться только по матчам **до** этого момента.
- Академические модели, использующие live-телеметрию матча (Skoltech, статья про LSTM/NN), достигают 80-93% точности — но это предсказание **внутри уже идущей игры**, а не до её начала, так что для целей Compendium (предматчевый прогноз) это не прямой ориентир, скорее показывает верхнюю границу, если Live-предсказания когда-то захочешь добавить отдельной фичей.

Практический вывод: для предматчевых командных прогнозов реалистичный ориентир точности — далеко не 90%+, и это нормально. Значение имеет калибровка (когда модель говорит "70%", команда А должна побеждать действительно примерно в 70% таких случаев), а не голая точность бинарного попадания.

## 6. Архитектура данных (как модули соединяются)

```
OpenDota / STRATZ / Steam API ──┐
                                  ├──► ingest.py ──► SQLite/Postgres ──► FastAPI ──► React-дашборд
Liquipedia (ростеры/трансферы) ──┘         │
                                            ├──► rating.py (Glicko-2)      → команды
                                            └──► fantasy_projection.py     → игроки
                                                 (новый модуль, раздел 4)
```

Оба аналитических модуля читают из одной и той же базы матчей — не нужно два отдельных пайплайна забора данных, только два разных способа агрегации уже собранных матчей.

## 7. Этапы разработки

1. **Фаза 1 — команды.** Ingest матчей, Glicko-2, Monte-Carlo по группам и сетке, простой дашборд. (Ядро — рейтинг и симуляции — уже реализовано и протестировано в этом чате; остался ingest под реальные данные и фронтенд.)
2. **Фаза 2 — игроки/Fantasy.** Разбор полей матча по игрокам, построение распределений по категориям очков, проекция на формулу из раздела 4.2, топ-3 рекомендации на слот (керри/мид/саппорт).
3. **Фаза 3 — полировка.** Обновление данных по расписанию, Tauri-сборка под ПК, ручная калибровка весов после выхода официальных цифр TI15.

Когда будешь готов — возвращаемся к скелету (бэкенд уже частично готов) и добавляем модуль из раздела 4.
